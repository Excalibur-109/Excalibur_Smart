RHI/Vulkan

Vulkan 后端：显式对象、状态与命令缓冲

rhi::RHIVulkan 将 RHI 描述映射到 Vulkan 1.3 风格的对象图：VkInstance、VkDevice、队列、内存、descriptor set、pipeline、command buffer 和 swapchain。它是本仓库最直接体现显式同步和动态渲染的后端。

构建状态源码完整存在，但当前根 CMakeLists.txt 的 RHI 目标仅列入 RHIVulkan.hpp，没有列入 RHIVulkan.cpp。这页描述的是源码实现，当前静态库尚未把其实现编入。

初始化：从描述到原生设备

Instance。收集 required/optional instance extension；请求验证时尝试 VK_LAYER_KHRONOS_validation 与 VK_EXT_debug_utils，再创建 VkInstance。
Surface。优先使用外部 VkSurfaceKHR；否则调用 createSurface(VkInstance)。surface 为空仍可离屏渲染与计算。
Physical device。枚举并打分，选择满足必需 feature 和 queue/surface 需求的设备。
Logical device。收集 device extension，若存在 surface 自动加 VK_KHR_swapchain；创建 graphics/compute/transfer/present queue。
基础池。创建 graphics command pool、timeline frame semaphore、按 framesInFlight 分配 primary command buffer，以及 descriptor pool。
Capabilities。把 Vulkan limits/features 整理为 RHICapabilities。

硬前提当前实现要求 Vulkan timeline semaphore support；如果设备不支持会初始化失败。graphics pipeline 还要求 device 支持 dynamic rendering。

公开原生句柄

RHIVulkanNativeHandles 暴露 instance、physicalDevice、device、surface、graphics/compute/transfer/present queue 及四个 queue family index。它适合调试或与既有 Vulkan 教程代码互操作；正常上层逻辑仍应停留在 RHI 句柄层。

管线

CreateGraphicsPipeline 读取 RHIGraphicsPipelineDesc，临时创建 shader modules、组装 vertex input/input assembly/raster/depth-stencil/multisample/blend/dynamic states，并以 dynamic rendering 的 attachment formats 创建 VkPipeline。每个 RHIShaderDesc::stage 必须恰好只有一个 bit；否则 toVkSingleShaderStage 抛错。

CreateComputePipeline 创建单个 compute stage 和 VkComputePipelineCreateInfo。两个创建函数都会使用可选的 VkPipelineCache。创建管线的临时 shader module 随后被销毁，pipeline 本身不依赖其继续存活。

CreateQueryPool 映射到 VkQueryPool；GPU 等 GPU 信号映射 binary 或 timeline VkSemaphore；CPU 等 GPU 信号映射 VkFence。

RenderGraph 帧录制

RecordAndSubmitFrame 选择一个 frame context，等待其 timeline value，reset/begin command buffer，处理 uploads，创建 graph 的 transient 资源，遍历已编译 pass 的 transition，再执行 workload。Raster pass 使用 vkCmdBeginRendering/vkCmdEndRendering；draw/indexed draw/dispatch 分别调用 Vulkan 命令，最后结束命令缓冲、提交 queue，并把 staging/transient 资源延后到对应 frame 完成后清理。

官方模型补充：对象、内存与所有权

Vulkan 的对象由创建它的 instance 或 device 管辖。销毁父对象前，必须先销毁或释放所有依赖的子对象；例如销毁 VkDevice 前应处理由它创建的 pipeline、image view、image、buffer、descriptor pool 与同步对象。仓库的 RHIVulkanDestroy.inl 使用延后释放来避免 CPU 先于 GPU 销毁资源，但这不替代等待相关提交完成，也不免除父子销毁顺序。

规范把资源对象和内存对象分离：vkCreateBuffer/vkCreateImage 只定义资源，随后应根据 vkGet*MemoryRequirements 的 size、alignment、memoryTypeBits 选择兼容 memory type，再分配并绑定。当前实现多数资源按对象单独 vkAllocateMemory；这易于学习和排错，但小资源过多时会造成分配数量和碎片问题。生产路径通常使用子分配器，或使用 Vulkan Memory Allocator 一类方案。

持久映射不等于 CPU 写入自动对 GPU 可见。非 HOST_COHERENT 内存写入后需要在按 nonCoherentAtomSize 对齐的范围上 vkFlushMappedMemoryRanges；CPU 读取 GPU 写入的映射内存前则需要 invalidate。此实现会选择 host-visible 内存并映射，但调用方仍应将一致性和同步作为独立问题审查。

与当前实现的边界不要根据 RHIHandle 仍然有效就推断原生对象仍可使用。RHI 句柄、资源表条目、延后销毁队列与 Vulkan 的 GPU 完成顺序是四个不同层次；真正安全的销毁前提是所有引用它的已提交工作都已完成。

官方模型补充：同步、layout 与动态渲染

Vulkan barrier 同时表达执行依赖和内存依赖。source/destination stage mask 决定依赖覆盖的流水线阶段，access mask 指出发生过或将发生的读写，image barrier 还声明 old/new layout；它们都必须与实际使用匹配。仅把 image 从一个 layout 改成另一个而没有正确的 stage/access 范围，不能可靠地解决读写可见性问题。当前 frame 路径以 vkCmdPipelineBarrier 落实 RenderGraph transition，因此 graph 的 reads/writes 必须覆盖所有真实访问。

动态渲染中，vkCmdBeginRendering 的 attachment view、load/store、resolve 和 layout 共同定义 raster pass。attachment 在开始时必须处于声明的 layout，结束后的后继使用仍须由 barrier 转换；dynamic rendering 取消的是 render pass/framebuffer 对象，不是 attachment layout 与同步责任。仓库要求 dynamic rendering feature，正是该路径的原生前提。

descriptor set layout 决定 binding 的 type、count、stage visibility 和不可变 sampler；descriptor pool 决定可分配的 descriptor 数量。set 被 command buffer 使用期间不能任意重写、释放或让其引用的对象失效。当前后端从共享 pool 分配 set，学习时应特别检查 pool 容量、set layout 生命周期和已提交 command buffer 对 descriptor 的引用。

官方模型补充：交换链与时间线信号量

vkAcquireNextImageKHR 只表示某个交换链 image 已可供应用使用，不能把 timeline semaphore 传给它，仓库也明确使用 binary semaphore。提交渲染时应等待 acquire 信号，呈现时应等待渲染完成信号；遇到 VK_ERROR_OUT_OF_DATE_KHR 必须重建 swapchain，VK_SUBOPTIMAL_KHR 通常表示仍可使用但应尽快重建。重建前要保证旧 image 不再被 GPU 或 present engine 使用。

timeline semaphore 的 value 单调增加，可用于表达多帧完成点；binary semaphore 只能处理一次信号/等待周期。当前 frame context 以 timeline value 回收延后资源，但 acquire/present 仍须遵守 binary semaphore 的 WSI 规则。多 queue 方案还需要额外声明 queue-family ownership transfer；当前整帧只在 graphics queue 上执行，尚未进入这条路径。

官方阅读

本页的“官方模型补充”按规范规则解释，完整链接与条目用途见 官方资料：Vulkan。建议先读内存分配和同步示例，再带着具体的 RHIVulkanFrame.inl barrier 逐项核对。

建议的阅读顺序

  1. RHIVulkan.hpp 先看所有权和公开接口。
  2. RHIVulkanPrivate.inl 看 Impl、句柄表和映射。
  3. RHIVulkanCore.inl 追初始化和 capabilities。
  4. 按 Resources → Pipelines → SyncSwapchain → Frame 的顺序，随时回到 资源与枚举 页核对 RHI 意图。
