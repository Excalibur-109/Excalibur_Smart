RHI/D3D12

D3D12 后端：root signature、PSO 与显式状态

RHID3D12 与 Vulkan 一样是显式模型：资源有状态，命令先录进 command list，再由 command queue 执行，GPU/CPU 顺序用 fence 维护。但它用 descriptor heap 和 root signature 取代 Vulkan 的 descriptor set/pipeline layout。

构建状态该后端的实现文件尚未列入当前 RHI CMake target；它依赖 Windows 的 D3D12、DXGI 和 D3DCompiler 组件。这页按现有源码说明其行为。

初始化与公开句柄

RHID3D12Desc 包含 HWND、最低 feature level 和 WARP 回退开关。Core 创建 factory6、选择 adapter、创建 ID3D12Device、graphics command queue、command allocator、graphics command list、内部 fence 与 event，并初始化 CPU/Shader-visible descriptor heaps。

RHID3D12NativeHandles 暴露 factory6、adapter、device、graphicsQueue、commandAllocator、commandList、fence、fenceValue、feature level 与 HWND。这反映了 D3D12 的基本执行单元：资源不是自动执行，必须经过 command list → queue → fence。

管线：Root Signature + PSO

CreateGraphicsPipeline 要求有效 pipeline layout/root signature，临时编译或创建 graphics shader，选择 VS/HS/DS/GS/PS，生成 input layout、raster/depth-stencil/blend/multisample、RTV/DSV formats，最后调用 CreateGraphicsPipelineState。vertex shader 是必要项；非 graphics stage 会报错。

CreateComputePipeline 使用同一 root signature 和 compute bytecode 调用 CreateComputePipelineState。RHIPipelineCacheDesc::initialData 若存在，作为 CachedPSO 的输入。D3D12 pipeline cache 句柄本身在此实现中主要保存描述，而不等于一个可写回的 Vulkan pipeline cache 对象。

绑定时序绘制前需要设置 shader-visible descriptor heap、SetPipelineState、graphics/compute root signature，然后对 bind set 的每个条目设置 root descriptor table。创建 CPU descriptor 只是第一步。

队列范围尽管 RHI 有 Compute/Transfer queue 语义，当前 D3D12 后端公开和使用的是 graphics queue、一个 allocator 和一个 graphics command list。不要将 graph 的 async compute 标记当作已完成多 queue 并发。

官方模型补充：命令分配器、命令列表与 fence

D3D12 的 command allocator 存放命令记录所需的内存，command list 只引用这些内存。执行过某个 command list 后，必须等 GPU 不再使用它关联 allocator 的命令，才能 Reset 该 allocator；command list 必须先 Close，才可以 ExecuteCommandLists，而它的 Reset 仅能在关闭后进行。当前 frame 先等待内部 fence，再 reset allocator/list，符合这一基本生命周期；将它扩展成多帧并行时，要为每个 frame context 保留独立 allocator 与 fence value。

ID3D12CommandQueue::Signal 将 fence 推进到指定值，CPU 通过 GetCompletedValue/SetEventOnCompletion 等待；queue 之间则用 Wait 建立 GPU-GPU 顺序。当前公开的 RHI 同步对象不等于完整跨 queue 编排，整帧仍以一个 graphics queue 与内部 fence 完成回收。

官方模型补充：Descriptor Heap 与 Root Signature

CBV/SRV/UAV heap 和 sampler heap 各有 CPU-visible 与 shader-visible 两种用途。只有 shader-visible heap 能由 root descriptor table 让 shader 访问；一个 command list 同时只能绑定至多一个 shader-visible CBV/SRV/UAV heap 和一个 shader-visible sampler heap，切换 heap 可能打断硬件现有工作。因此，仓库从 CPU descriptor 创建 bind set，再在录制阶段准备 shader-visible 区域的做法是合理分层，但要控制每帧容量和 heap 重置时机。

root signature 是着色器可见资源的 ABI：descriptor table 指向 heap 中连续 range，root descriptor 直接提供 GPU virtual address，32-bit root constants 直接放入 command stream。它们在灵活性、根参数空间和描述符间接层之间权衡。当前实现将 bind-set layout 转成 descriptor table、将 push constant 转为 32BIT_CONSTANTS；变更 binding slot、range 或 visibility 时，HLSL register space 与 root signature 必须保持一致。

官方模型补充：资源状态、UAV 与别名

D3D12 要求应用保证资源在使用时处于正确 D3D12_RESOURCE_STATES。transition barrier 处理状态变化；UAV barrier 处理两次无序访问之间的全局顺序，即使状态不变；aliasing barrier 表示同一 heap 区间的旧 placed resource 与新 placed resource 交替使用。COMMON 是常用初始/交换状态，但状态 promotion/decay 是有条件优化，不能用来替代明确状态追踪。

当前 RenderGraph 已计算 alias slot，但 D3D12 后端为 transient 资源创建独立 committed resource，尚未把 alias slot 落为同一 heap 上的 placed resource，也未插入 aliasing barrier。这意味着图级“生命周期不重叠”的结论已经存在，实际内存复用与相应同步尚未接入；不能把 alias slot 当成已经节省了显存。

官方模型补充：DXGI flip model 与 resize

D3D12 的窗口交换链通常采用 flip model。调用 ResizeBuffers 前，必须释放所有 back buffer 资源与相关 descriptor 的使用关系，确保 GPU 不再访问旧 buffer；resize 后重新获取 back buffer 并重建 RTV。tearing 需要检查设备支持并在创建和 Present 阶段使用匹配 flags。当前实现采用 FLIP_DISCARD，但 resize/recreate 仍是调用端和后续后端功能需要系统化覆盖的情况。
