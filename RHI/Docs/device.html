RHI/Device

统一 Device 门面

Device 层的目标是把“选哪种 API”和“如何创建资源、提交、呈现”收敛成统一入口。它的公开接口已经勾勒出一个完整 RHI，但当前实现仍处于未完成状态。

真实缺口RHIDevice.cpp 目前没有实现 RHIDevice 的成员函数；CreateRHIDevice(const RHIDeviceCreateDesc&,...) 即使 Initialize 成功也会 return nullptr。因此不能把它当作可工作的后端工厂。学习具体资源和帧提交，请直接查看三个具体后端类。

设计边界

RHIDevice 位于公共层，理论上持有私有 Impl，向调用方暴露统一的创建、查询、提交与销毁接口。它不应该在头文件里泄露 VkDevice、ID3D11Device 或 ID3D12Device，否则上层会失去跨后端可移植性。

调用方：构造 RHIDeviceCreateDesc，只表达 API、特性、队列和窗口/Surface 的通用需求。
工厂：选择 RHIGraphicsAPI 对应的具体后端并把平台参数转入专用描述。
具体后端：创建原生 device 与资源表，返回 RHI 逻辑句柄。
门面：将所有调用转发到选中的后端，隐藏差异。

RHIDeviceCreateDesc：可移植输入

字段含义后端如何解释
backendRHIBackendDesc：应用/引擎名、preferredApi、功耗偏好、验证、必需/可选 feature、framesInFlight、crash dump、pipeline cache共同初始化意图；详细特性判断由具体后端写回 RHICapabilities。
nativeWindow不透明原生窗口指针D3D11/D3D12 解释为 HWND；离屏渲染可为空。
vulkanSurface已创建的 VkSurfaceKHR，以 uintptr_t 保存可直接交给 RHIVulkanSurfaceDesc::surface。
createVulkanSurface接收 VkInstance、返回 VkSurfaceKHR 的回调适合 GLFW/SDL 等必须在 instance 创建后生成 surface 的窗口层。
ownsVulkanSurface是否由 Vulkan 后端在 Shutdown 销毁 surface明确所有权，避免平台层和后端重复销毁。
required/optionalVulkan*Extensionsinstance 与 device 扩展列表Vulkan 初始化逐项验证 required，选择可用 optional。
queuesRHIQueueDesc 列表表达 Graphics/Compute/Transfer/Present 的期望；Vulkan 当前实际每 family 取一个 queue。
allowSoftwareAdapter是否允许软件适配器D3D 后端可回退到 WARP。

理论上的统一公开接口

接口组RHIDevice 方法抽象意义
生命周期Initialize、Shutdown、IsInitialized、Api、BackendNamme、Capabilities创建和查询后端；能力应作为选择渲染路径的依据。
资源CreateBuffer、CreateTexture、CreateTextureView、CreateSampler、CreateShaderModule创建 GPU 数据和访问视图。
绑定/管线CreateBindSetLayout、CreateBindSet、CreatePipelineLayout、CreatePipelineCache、CreateGraphicsPipeline、CreateComputePipeline把 shader 接口与固定功能状态编译为可绑定对象。
查询/同步/呈现CreateQueryPool、CreateGPUWaitGPUSignal、CreateCPUWaitGPUSignal、CreateSwapchain、GetSwapchain*、AcquireNextImage、Submit、Present控制帧的可显示目标和 CPU/GPU 执行顺序。
整帧SubmitFrame、WaitIdle把 RHIFramePacket 与 RenderGraph 路径连接到 native command recording。
销毁所有资源类型的 Destroy 重载按逻辑句柄释放实际对象；无效/已销毁句柄应安全忽略。

接口拼写头文件里的方法名是 BackendNamme()，含两个 m。文档按源码保留拼写；在真正实现门面前应修正为 BackendName() 并同步调用点。

为什么当前应直接学习具体后端

具体类 rhi::RHIVulkan、RHI::RHID3D11、RHI::RHID3D12 已经声明完整而几乎一致的公开生命周期 API，且每个方法都在 *Core.inl、*Resources.inl、*Pipelines.inl、*SyncSwapchain.inl 或 *Frame.inl 有实现。它们是现在可以逐行学习的真实路径。

// 当前工厂的实际控制流（简化）
std::unique_ptr<RHIDevice> CreateRHIDevice(const RHIDeviceCreateDesc& desc, ...) {
    auto device = std::make_unique<RHIDevice>(desc.backend.preferredApi);
    if (!device->Initialize(desc, ...)) return nullptr;
    return nullptr; // 当前源码的未完成返回值
}

补全门面时应遵守的顺序

  1. 在 RHIDevice::Impl 中使用 std::variant 或多态后端接口保存三种具体后端之一。
  2. 将 RHIDeviceCreateDesc 无损转换为 RHIVulkanDesc、RHID3D11Desc 或 RHID3D12Desc。
  3. 逐个转发创建、查询、提交与 Destroy；不要在门面里重新实现资源表。
  4. 成功初始化后返回已初始化的 unique_ptr<RHIDevice>，而不是 nullptr。
  5. 把三个后端 .cpp 加入 CMake 目标，并按平台条件链接 D3D 库；编写每个后端的最小初始化测试。
