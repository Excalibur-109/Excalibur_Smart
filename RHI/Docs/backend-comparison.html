如何做正确的跨 API 设计

  1. 将资源用途写在 usage，将每个 pass 的访问写在 reads/writes，不要把某 API 的 layout/descriptor heap 细节上浮到业务层。
  2. 每帧根据 RHICapabilities 选择 feature 路径；不要仅因为枚举存在就假设当前设备和后端都实现了它。
  3. 在 D3D11 路径特别检查资源读写冲突和状态清理，因为它是隐式状态机；在 Vulkan/D3D12 路径特别检查 state/barrier 和命令提交顺序。
  4. 把“对象可创建”和“workload 已可录制”分开测试。query pool 存在并不表示 query command 已进入 frame 路径。
  5. 处理失败时读取 errorMessage 或异常文本；这些实现对不支持路径多数会明确报错，而不是静默跳过。

主题Vulkan 官方模型D3D11 官方模型D3D12 官方模型对 RHI 的含义

因此，跨 API 的“正确”不是把所有后端强行伪装成同一条命令序列，而是统一资源意图、pass 依赖和能力查询，并在边界处保留同步、状态、descriptor 与呈现的原生规则。官方链接与适用范围见 官方资料。
